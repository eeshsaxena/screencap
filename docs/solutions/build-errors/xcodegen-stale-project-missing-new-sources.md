# XcodeGen-generated project went stale, silently dropping newly added Swift files from the build

## Problem
The macOS app failed to build with a cluster of `cannot find ... in scope` errors after a feature branch added new Swift files. The build script never regenerated the XcodeGen project, so `xcodebuild` compiled a stale file list that referenced new symbols but excluded the files defining them.

## Symptoms
- `cannot find 'UploadCoordinator' / 'CloudAuthController' / 'ReviewWindow' / 'ReviewWindowID' / 'ReviewWindowOpener' in scope`
- `type 'NSNotification.Name?' has no member 'reviewWindowUploadSucceeded'`
- Every unfound symbol is defined in a file that is present on disk but missing from the compiled `ScreenCap.SwiftFileList`.

## Root Cause
`macos/ScreenCap.xcodeproj` is git-ignored (see `macos/.gitignore`) and generated by XcodeGen from `macos/project.yml`, which globs the `ScreenCap/` and `ScreenCapTests/` source trees **at generation time** and writes the file list into `project.pbxproj`.

The freshness check in [`generate_project_if_needed()`](../../../script/build_and_run.sh) regenerated only when one of three things was true:

1. The `.xcodeproj` directory was missing, or
2. `project.yml` was newer than `project.pbxproj`, or
3. `DEVELOPMENT_TEAM` was set.

None of these detect a changed **source tree**. PR #218 (`feat/native-redaction-review-upload`) added 15 Swift files (`Views/Review/*`, `UploadCoordinator.swift`, `CloudAuthController.swift`, `ReviewWindowOpener.swift`, etc.) without changing `project.yml`, so the stale project survived and `xcodebuild` compiled the old 33-file list — which still *included* the PR-modified old files (`ScreenCapApp.swift`, `RecordingsIndex.swift`) that now referenced the new, uncompiled symbols.

## Solution
Add a freshness condition that regenerates when the **source tree structure** is newer than the generated project, using **directory** mtimes:

```bash
elif [[ -n "$(find "$MACOS_DIR/ScreenCap" "$MACOS_DIR/ScreenCapTests" -type d -newer "$PROJECT_FILE/project.pbxproj" -print -quit 2>/dev/null)" ]]; then
  # xcodegen globs sources at generation time, so adding/removing/renaming a
  # source file changes the project's file list without touching project.yml.
  # Those operations bump the containing directory's mtime (plain content
  # edits do not), so a source dir newer than the generated project means the
  # baked-in file list is stale.
  should_generate=1
```

To recover an already-broken checkout immediately, run `cd macos && xcodegen generate` (or just delete `macos/ScreenCap.xcodeproj` and let the build script regenerate it).

## Why This Works
Adding, removing, or renaming a file updates the **containing directory's** mtime; editing a file's *contents* does not. Those directory-changing operations are exactly the ones that change XcodeGen's globbed file list. Checking `-type d -newer` therefore triggers regeneration precisely when the file list is stale, and stays quiet on ordinary code edits — so it doesn't regenerate (and invalidate incremental builds) on every save. Verified in a sandbox: regenerates on file-add, skips when the project is already fresh, skips on content-only edits; the real build then reported `BUILD SUCCEEDED`.

## Prevention
- Any freshness/caching guard around a **glob-at-generation-time** artifact (XcodeGen, and similar generators) must key off source-tree structural changes, not just the spec file.
- Prefer **directory** mtimes over file mtimes to distinguish structural changes (add/remove/rename) from content edits.
- Tool-native alternative: `xcodegen generate --use-cache` hashes all globbed inputs and regenerates only when they change. It's the most robust option and avoids hand-rolled freshness logic; the directory-mtime check was chosen here to stay within the script's existing explicit-condition style.
