# On-device segmentation silently falls back to the idle-gap heuristic (helper unreachable from the nested daemon bundle)

## Problem

On-device day-splitting (Apple Foundation Models via the bundled `IntelligenceHelper`) never actually ran. Every recording — including on a macOS-26 machine with `llm_provider = on-device` — silently degraded to the mechanical idle-gap heuristic, so tasks came out named `task_1`, `task_2`, … and split at arbitrary inactivity gaps instead of by the model.

## Symptoms

- Library/Journal task lists show `task_1`, `task_2`, … at meaningless boundaries.
- The recording's `tasks.json` has `"source": "idle_gap_heuristic"` (and no `category`/`confidence` metadata) even though the on-device provider was selected.
- Nothing errors — the whole path is fail-open, so there is no crash, no 500, and no default-level log line pointing at the cause.
- Reproduces on macOS 26 (Apple Silicon), contradicting the assumption that the heuristic only affects Intel / pre-macOS-26 Macs.

## What Didn't Work

- **Suspecting the OS floor / Apple Intelligence enablement.** The machine was macOS 26 (Darwin 25.x), where Foundation Models is supported. The provider never even spawned the helper, so OS/model enablement was upstream-irrelevant.
- **Suspecting the fail-closed privacy gate.** `build_activity_summary` correctly set `stripped=True` for the local path, so `OnDeviceProvider.segment` passed the gate — not the blocker.
- **Assuming a genuine empty model result.** A `None` (ran, no tasks) would leave the recording *unnamed*, not produce `task_1…task_N`. The mechanical names are emitted only by `_heuristic_local_tasks`, which fires only on `PROVIDER_UNAVAILABLE` — proving the helper was never located.

## Solution

Root cause was in `OnDeviceProvider._find_bundled_helper()` (`src/screencap/segmentation/providers/ondevice.py`): it walked up to the **first** `Contents` ancestor and returned `None` if the helper was not in *that* bundle's `MacOS/`.

After SCR-196 the daemon runs from a **nested** `ScreencapDaemon.app`
(`ScreenCap.app/Contents/Library/LoginItems/ScreencapDaemon.app`), whose own `Contents/MacOS` carries no helper — the app's "Embed IntelligenceHelper" build phase copies `IntelligenceHelper` only into the **outer** `ScreenCap.app/Contents/MacOS/`. Discovery stopped at the nested bundle and never reached the outer helper → `PROVIDER_UNAVAILABLE` → idle-gap heuristic. Dev-source (Debug) daemons failed identically: they run from the repo with no app-bundle ancestry at all, and the launcher never exported a helper path.

Two complementary fixes (PR [#353](https://github.com/proteus-computer-use/screencap/pull/353)):

1. **Walk every `Contents` ancestor** — skip a helper-less bundle and keep climbing to the outer app:

```python
# Before — stops at the first Contents (the nested daemon bundle):
for parent in Path(__file__).resolve().parents:
    if parent.name == "Contents":
        candidate = parent / "MacOS" / _HELPER_BASENAME
        if candidate.is_file() and os.access(candidate, os.X_OK):
            return candidate
        return None            # <-- gives up before the outer app
return None

# After — a strict superset of the old single-bundle behavior:
for parent in Path(__file__).resolve().parents:
    if parent.name == "Contents":
        candidate = parent / "MacOS" / _HELPER_BASENAME
        if candidate.is_file() and os.access(candidate, os.X_OK):
            return candidate
        # not in THIS bundle's MacOS — keep walking up to an ancestor bundle
return None
```

2. **Have the launcher export the exact path** — the daemon launcher generated by `macos/ScreenCap/Scripts/embed-cli.sh` (both Debug and Release heredocs) lives in the outer app's `Contents/Resources`, so it knows the layout. It exports `SCREENCAP_ONDEVICE_HELPER` before every `exec`, which `_resolve_helper()` prefers over the walk-up. This one line covers the nested-daemon **and** dev-source cases (dev has no bundle ancestry, so the walk-up alone cannot help it):

```sh
if [ -z "${SCREENCAP_ONDEVICE_HELPER:-}" ] && [ -x "${SCRIPT_DIR}/../MacOS/IntelligenceHelper" ]; then
    SCREENCAP_ONDEVICE_HELPER="${SCRIPT_DIR}/../MacOS/IntelligenceHelper"
    export SCREENCAP_ONDEVICE_HELPER
fi
```

## Why This Works

The helper only ever ships in the outer `ScreenCap.app/Contents/MacOS/`, but the code that discovers it runs from a *different, nested* bundle. Discovery has to bridge that gap. The walk-up now reaches the ancestor bundle that actually holds the helper, and the launcher — the one component that unambiguously knows the outer-app layout — passes the path explicitly, which is more robust than any process guessing via filesystem introspection from wherever it happens to be imported.

## Prevention

- **Any daemon-side "walk up to find a resource in the app bundle" must account for the nested `ScreencapDaemon.app` (SCR-196).** The daemon's own bundle intercepts the walk *before* the outer `ScreenCap.app`. Prefer having the outer-app launcher export an explicit path over the daemon inferring one.
- **Test bundle-layout discovery against real layouts, not just the env-var seam.** This shipped because `_find_bundled_helper()` had zero coverage — every existing test used the `SCREENCAP_ONDEVICE_HELPER` override. `TestBundledHelperDiscovery` now pins four layouts: outer-app `Contents/Resources`, nested-daemon (regression guard), no-bundle, and helper-less `Contents`.
- **Watch fail-open degradation paths — they hide integration breaks.** Because segmentation degrades silently to the heuristic rather than erroring, a totally broken on-device path produced *plausible* output. A `source: idle_gap_heuristic` marker on a recording whose provider was on-device is the tell; consider surfacing an observable signal (log/metric) when a selected provider degrades unexpectedly.
- **When relocating where a process runs inside a bundle, re-audit every path that resolves resources relative to `__file__` or the executable.** SCR-196 moved the daemon; discovery logic written for the old `Contents/Resources` location was not revisited.
