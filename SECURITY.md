# Security Policy

ScreenCap captures screen content, audio, keystrokes, and window context, all of which can be sensitive. This document explains the security boundary the recorder runs behind, the threats it does and does not defend against, and how to report a vulnerability.

## Trust boundary

The ScreenCap daemon listens on a UNIX domain socket at `~/.screencap/run/api.sock`. The directory is created with mode `0o700` and the socket file with mode `0o600`, so only processes running as the same macOS user account can connect. When a connection is accepted, the daemon also verifies via `getpeereid()` that the peer's effective UID matches the daemon's own EUID, and rejects any other connection. Together, the filesystem permissions and the EUID match define the daemon's authentication boundary: **a same-EUID process can call any daemon verb; nothing else can.**

This is the same boundary used by `ssh-agent`, `gpg-agent`, the Docker daemon, and Apple's own non-XPC daemons. The Apple Platform Security Guide treats the user account as the primary data-protection boundary on macOS; in-process privilege separation is layered on top via TCC, the App Sandbox, and code signing, not via finer-grained socket auth. ScreenCap follows the same posture deliberately, and SCR-64 ratified it after considering two stricter alternatives (see [Alternatives considered](#alternatives-considered)).

The Phase 1 and Phase 2 daemon architecture plans (`docs/plans/2026-05-08-001-feat-daemon-architecture-phase-1-plan.md` and `docs/plans/2026-05-08-002-feat-daemon-architecture-phase-2-plan.md`) both named filesystem permissions plus `getpeereid()` as the v1 authorization surface and deferred any in-band auth header to a future iteration. This document formalizes that position.

### Defense in depth around the boundary

Several mechanisms harden the boundary without changing what authenticates a caller:

- **Bind-time permission verification.** At startup, the daemon re-stats both the socket file and its parent directory and refuses to listen if either deviates from the expected mode. This catches umask drift, accidental `chmod` post-install, and tampered run-dirs before the daemon ever serves a request. See `src/screencap/daemon/socket.py`.
- **Per-call audit log.** Every `/v0/recording.start` and `/v0/recording.stop` invocation appends a JSON-lines record (timestamp, verb, peer PID, peer binary path, provenance classification, outcome) to `~/.screencap/run/audit.log` (mode `0o600`). The log is best-effort — write failures degrade to a logger warning and never block the verb — but provides a forensic trail under the same-EUID trust model. Read-only verbs (`recording.list`, `session.snapshot`, `daemon.info`, `events`) are intentionally not audited because they leak no capability.
- **Server-derived `started_by` provenance.** The daemon classifies every caller as `swiftui` / `cli` / `mcp` / `unknown` from the peer's effective PID, binary path, and argv, and uses that classification as the authoritative `started_by` on persisted metadata. The classification is advisory only; it does not gate access to any verb.

## Cloud auth trust boundary

ScreenCap's optional cloud upload/download is governed by a boundary separate from the daemon socket. Sign-in, per-user storage isolation, and the public demo gallery follow the properties below (see `docs/plans/2026-05-29-002-feat-per-user-cloud-storage-isolation-plan.md` and `docs/runbooks/cloud-auth-setup.md`).

- **The signing Cloud Function is the authorization boundary, in code.** It verifies a Firebase ID token and scopes every upload/list/download to a per-user `users/{uid}/…` prefix through a single key builder (`resolve_prefix`). The function stays `--allow-unauthenticated` at the Cloud Run layer **by design** — there is no Cloud Run IAM backstop — so the in-code gate is the only boundary. It is enforced by a CI contract test that asserts no tokenless request can reach any `users/` code path, and a per-action test that no unauthenticated request resolves outside the public `demo/` namespace.
- **The owner id is the verified Firebase `uid`, never the email.** The `uid` is immutable, opaque, and path-safe; emails are mutable and would leak PII into cloud-bound object paths. The function pins the trusted Firebase project (`SCREENCAP_PROJECT_ID`) and re-asserts the token's `aud`/`iss` so it cannot verify-but-misattribute a token from a foreign project.
- **Refresh token in a shared Keychain access group (SCR-241).** The long-lived Firebase refresh token (`screencap-auth`) is stored on the macOS **data-protection keychain** in a **team-shared access group** (`2A8S6MV8DZ.com.screencap.shared`, `kSecAttrAccessGroup`), device-local (`kSecAttrSynchronizable=false` — never iCloud-synced) and readable after first unlock so the all-day daemon can read it while the screen is locked. Every same-Team-signed ScreenCap binary carrying the `keychain-access-groups` entitlement (the app's embedded daemon + bundled CLI, one identity) reads it **without a prompt**; a binary not entitled for the group (the pip/pyenv terminal CLI, the Debug fallback) gets `errSecMissingEntitlement` and falls back to the legacy `keyring` login-keychain path, where it stays a **separate** credential. This **widens** silent readability from a single per-binary code identity (the old `keyring` ACL) to *any* same-Team-signed binary — a deliberate change that does **not** cross the same-user boundary below (any same-EUID process could already read the token) and that removes a cross-binary authorization prompt with no security value. On upgrade, a pre-existing legacy item is migrated into the group via a **strictly non-interactive** read+delete that can never prompt; when it can't be read silently the user signs in again (the token is recoverable). This is still **NOT** a code-signing-pinned secret. The short-lived ID token is held only in memory. **Asymmetry (partially resolved):** the cloud E2EE KEK now lives in the same shared access group with a hardened migration (see "Client-side cloud encryption" below — the KEK is *unrecoverable*, so its migration deletes the legacy item only after a verified readback of the group item, unlike the recoverable token's fail-open move). The network-capture KEK (`src/screencap/network/crypto.py`) still uses the default per-binary ACL; migrating it remains deferred.
- **Signed URLs are unrevokable bearer capabilities for their lifetime.** A v4 signed URL cannot be revoked before it expires, so private (`users/`) GET URLs use a short 30-minute window; the public `demo/` namespace uses a 4-hour window because it serves only consented, curated content. Upload (PUT) URLs expire in 15 minutes.
- **`--network` cannot capture your own credentials.** The OAuth, `signInWithIdp`, and token-refresh hosts are excluded from `--network` HTTPS interception even when the user overrides the default blocklist, and the capture proxy refuses to start if any required host is missing (fail closed).
- **Daemon cloud-credential containment.** The live-recording upload path is now wired, and the containment it relies on is live: the long-lived refresh token stays in the foreground/login context and is never handed to the daemon. The all-day daemon and its engine subprocess receive only a short-lived ID token, delivered out-of-band via a `0600` file path (passed as a path, never on the command line where `ps` could read it). The daemon re-mints + rewrites that file on a timer so a recording can outlast the ~1h token, and a token failure fails closed — the recording stays local (it is never deleted).

### Cross-account recording isolation (SCR-116)

A cloud-bound recording is **pinned at start to the account that owns it**, so a mid-lifecycle account switch (`screencap logout && login` as another user) can never converge it into a second user's namespace. This is the client-side complement to the server authority above: it only ever *refuses* a cross-account action, never *authorizes* one.

- **The server stays the namespace authority; the client only refuses.** `auth.id_token_uid()` decodes the Firebase `uid` from an ID token **without verifying it**, and that uid is used *only* to refuse a cross-account convergence (fail closed) — never to authorize one and never to choose a `users/{uid}` prefix. The signing Cloud Function remains the verifier of record (it re-verifies the token and pins the project, as above). A malformed or uid-less token decodes to "unknown," which can only relax the gate, never tighten it against the wrong account.
- **`.cloud_owner_uid` is local-only ownership metadata.** The owning uid is written into the recording directory as `.cloud_owner_uid` by the daemon at recording start — and only when the staged token carries a resolvable uid (a malformed token or a write error leaves the recording unpinned rather than failing the start). It is the **same sensitivity class as `.recording_intent`**: a dotfile, so `upload.list_recording_files` (which skips every `.`-prefixed name) never includes it in any uploaded set. It never leaves the machine.
- **Enforcement: a determined account mismatch refuses every cloud op and keeps the recording local.** At convergence (`terminal_stage._route_cloud`), if the recording carries a pin and the currently signed-in uid is determinable and **different**, the terminal stage refuses every cloud operation — no scrubbed copy produced, no upload, no completeness sentinel, no eviction — and leaves the recording intact on disk. For a `both`-destination recording this keeps the local copy but means it does not reach its cloud half until the user signs back into the owning account. This refusal — not the relaxation below — is the gate's primary purpose.
- **Deliberate fail-open degradation (the accepted residual).** The gate refuses **only** on a determined, different uid. Two cases deliberately degrade to prior behavior instead: a recording with **no pin** (legacy, or a local recording never tied to an account) has nothing to honor, and an **undeterminable current account** (not signed in, or a transient auth failure) is treated as "cannot confirm," not as a switch. The second is the one accepted residual where the "never fragment" invariant relaxes — the design deliberately chooses *never false-refuse* over *never fragment*, so a transient inability to read the current uid falls through to the normal fail-closed upload path rather than wrongly refusing a legitimate same-account upload. `tests/test_terminal_stage.py::TestSCR116AccountOwnershipGate` pins all four cases (mismatch refuses, match proceeds, no-pin proceeds, undeterminable-uid proceeds).
- **A complementary in-memory guard covers the live path.** While a recording is live, the daemon's token re-mint loop (`daemon/supervisor.py`) refuses to restage the engine token when a re-minted token's uid changes (a determined account switch), so the engine keeps the original account's token and fails closed on expiry. It applies the *same* determined-different-uid-only tolerance (a `None` / undeterminable re-mint uid is not a switch). The terminal-stage gate backstops the entry points that guard cannot reach — daemon resume and `screencap upload`, which read the current account from the Keychain rather than from the engine token. The two layers read **different uid sources** by design, which is why both exist.

### Client-side cloud encryption (E2EE upload, opt-in beta — default off)

An optional client-side encryption layer makes a cloud upload unreadable by the server. It is gated by `cloud_e2ee_enabled` (`SCREENCAP_CLOUD_E2EE` / config `cloud_e2ee_enabled`, **default `false`**) and is now a user-facing **opt-in beta**: the Privacy settings row (or `screencap e2ee enable`) turns it on after a limits disclosure. The enable flow creates the key **first** and sets the flag only on success, so there is no window where the flag is on with no key; `screencap e2ee disable` writes an explicit `false` (never unsets, so a future default change cannot silently re-enroll an opt-out) and keeps the key for re-enable. When off, uploads are plaintext exactly as before.

- **The client encrypts before upload; the server holds only ciphertext.** A cloud recording's artifacts are encrypted on-device (AES-256-GCM, framed — `src/screencap/cloud_crypto.py`) *after* the existing privacy scrub and *before* the signed-URL PUT, at every upload site (the batch/terminal seam in `upload.py` and the live during-recording seam in `chunk_processor.py`). The signing Cloud Function and object store never see plaintext, and the signer needs no change — it only signs URLs, never reads bytes. This is a stronger claim than the network-body or at-rest encryption: it protects recordings from the server itself, reversing the prior server-readable posture.
- **The encrypt decision is frozen per recording, not read live.** `cloud_e2ee` is frozen into `.recording_intent` at recording start, and every upload seam derives its encrypt-vs-plaintext decision from that frozen bit — the live flag's only role is seeding it. A recording started under E2EE therefore encrypts (or fails closed without a key) even if the flag is flipped off mid-life, which is what makes the Library's per-recording "uploaded · encrypted" badge truthful: a badge can never claim encryption for a recording that shipped any plaintext object. Disabling E2EE affects only recordings started after the disable.
- **Shared-access-group key; syncs to the user's own Macs via iCloud Keychain (SCR-253, Stage 2).** The cloud key is a 256-bit key in the data-protection keychain under the team-shared access group (same group and headless-read posture as the auth refresh token above), created only in a foreground context (`screencap e2ee enable` or `screencap login`). It is written **`kSecAttrSynchronizable=true`**, so it syncs to the user's other Macs signed in with the same Apple ID and iCloud Keychain on — the mechanism that lets a second Mac decrypt without a per-recording key exchange. iCloud Keychain is **end-to-end encrypted under standard data protection** (Apple cannot read synced item contents; Advanced Data Protection is not required), and the item carries no `SecAccessControl` and no persistent reference (both of which would block syncing). Un-entitled binaries (pip/pyenv CLI, ad-hoc dev builds) fall back to the legacy login-keychain `keyring` home and do **not** sync; a pre-existing legacy key migrates to the group once, strictly non-interactively, deleting the legacy item **only after a verified readback** of the group copy. All group-KEK writes are **add-only** (`keychain_group.add_if_absent`, never add-*or-update*), so a would-be second mint or a synced copy racing in from another Mac is kept, never overwritten — a user's ciphertext cannot fork by overwrite. **Residual (multi-Mac Stage-1):** the anti-fork guarantee is for a *single* device; if a beta user enabled E2EE on **two** Macs during Stage 1 — before any sync existed — each minted an independent key, and turning on sync cannot merge two AES keys. iCloud Keychain reconciles the conflicting synced items to one value, so the other Mac's Stage-1 recordings become undecryptable under the surviving key. Add-only + never-delete (below) keeps each Mac's own device-local key intact so it can still decrypt *its own* recordings locally; genuine cross-device recovery of both key sets is deferred (device-enrollment key wrapping, SCR-221/SCR-229). This is documented, not silently handled.
- **Custody honesty and the delete-propagation hazard (KTD-5/KTD-6).** Because an encrypted copy of the key transits iCloud and is escrowed in Apple's HSM (recoverable with the device passcode + Apple ID), a copy of the key *does* leave the user's Macs — so "keys never leave your devices" is off the table; the honest claim is **"neither we nor Apple can read your recordings."** Key security now inherits the strength of the user's device passcode and Apple ID. Two constraints follow. (1) Every KEK **read** matches either sync flavor (`keychain_group.SYNCHRONIZABLE_ANY`), so a Stage-1 device-local (`synchronizable=false`) key is always found and never mistaken for absent — which would mint a forking second key. (2) **Deleting a synchronizable item propagates to all the user's Macs** — a KEK-delete bug is fleet-wide data loss — so **no product path deletes a group KEK item at all**. The sync-on rewrite *adds* a synchronizable copy and **keeps** the byte-identical device-local item as a durable on-device fallback (it cannot fork, and it survives the user later turning iCloud Keychain off or signing out of their Apple ID, which can purge synchronizable items locally). `e2ee disable` keeps the key; the `SYNCHRONIZABLE_ANY` sentinel is structurally rejected by every add/update/delete primitive; and a source guard pins that no `keychain_group.delete` of the synced flavor exists anywhere in the tree.
- **Still no key recovery of our own (SCR-252); a keyless Mac gets guidance, not a corruption error.** There is no ScreenCap-built escrow or recovery: if the user has no Mac holding the key and cannot recover it through iCloud Keychain, every recording encrypted under it is permanently undecryptable, and a header key-id mismatch surfaces that as a distinct "key lost" error. iCloud Keychain has **no key-presence API**, so the "second Mac can't decrypt yet" case (iCloud Keychain off on the writing Mac, or the key not yet synced) is handled as **guidance, not detection**: the app routes an encrypted, locally-absent recording to a "sign in · turn on iCloud Keychain" message (`InspectRouting`), and the `download` CLI reports a distinct key-unavailable marker and exits non-zero — never a decode-failure that reads as corruption.
- **The key raises the stakes of the same-EUID concession.** As with the refresh token and network KEK, any same-user "Always Allow"-trusted binary can read the cloud key — but this key now guards the "server can't read your recordings" claim, not just at-rest copies, so the concession matters more. It is stated honestly rather than claiming a pinning that does not exist.
- **Engine key delivery mirrors the token channel, hardened.** The live-upload path runs in the engine subprocess, which cannot read the Keychain. The daemon reads the key in its own ACL context and delivers it out-of-band via a `0600` file (path passed in the environment, never on the command line), created `O_CREAT|O_TRUNC|O_NOFOLLOW` — the `O_NOFOLLOW` symlink guard is the load-bearing hardening — in the `0700` run dir and unlinked when the engine exits and on daemon shutdown. Unlike the token, the static key is never re-minted and never persists beyond the recording. A missing key fails the upload **closed** (the chunk is marked FAILED and nothing is deleted); it never falls back to a plaintext upload.
- **Encrypted recordings are viewable only in the app; the server-side pipeline no-ops on them, by decision.** The macOS app downloads and decrypts on-device (`src/screencap/download.py`, verify-then-write to a `0600` temp file and atomic-replace, so a tampered or truncated object leaves no partial plaintext). Everything server-side that reads artifact *contents* is incompatible with ciphertext by construction: the public website's direct-from-GCS player, and the Eventarc `process-recording` service (`scripts/process-recording/main.py`) that parses `recording_complete.json` + manifests for session stitching, the website index, and enrichment. Under E2EE that pipeline no-ops — and that is the **decided posture** (SCR-220 plan, KD5), not an open question: web playback and server enrichment apply only to server-readable uploads. The only server-readable path going forward is a future, separately-consented training-corpus lane; the E2EE default claim never extends to it.
- **`recording.db` remains local-only, unchanged.** Encryption changes only *how* the already-uploadable, already-scrubbed artifacts are sent — never *what* is sent. The R8 exclusion of `recording.db`, its sidecars, and `*.scrub_failed` runs before both encryption seams.
- **Every claim is bound to the runtime signal for the capability it describes.** Onboarding still makes no end-to-end-encryption / "we can't watch" / pricing claim (enforced by the `OnboardingStepPolicy` honesty-gate test — those unlock only when E2EE is the default). The Privacy settings row's copy is state-keyed: the truthful multi-device beta claim (the key syncs to the user's own Macs; neither we nor Apple can read the recordings) renders only when `cloud_e2ee_enabled` is actually on (`PrivacySettingsPolicy` + its string-gate tests), and "always on", "shared · encrypted", "keys stay with your team", and the retired Stage-1 "only this Mac can decrypt" claim remain forbidden in every state until the capabilities behind them exist.

## Cloud recording privacy: capture-time blocking vs. post-hoc masking

The unified recording pipeline (the "disk-first pipeline" refactor) captures **rich chunks to disk as the source of truth** and converges each recording toward its destination through a single terminal stage that owns the cloud-bound scrub/mask transform. Two facts define the cloud-video privacy boundary, and the boundary differs depending on a single config flag, `masked_video_upload` (`SCREENCAP_MASKED_VIDEO_UPLOAD`, **default `false`**):

- **`recording.db` is local-only, by rule (never uploaded).** The raw `recording.db` holds unscrubbed PII (window titles, event text) and now also hosts the per-chunk pipeline ledger. It is the local source of structured truth and is **never** part of any uploaded set — enforced by one explicit deny rule applied at every enqueue path: the post-recording upload seam excludes the raw artifacts by full relative path (`upload.list_recording_files` drops `recording.db`, its `-wal`/`-shm` sidecars, and `*.scrub_failed`, so nested copies are excluded too), and the `upload.assert_uploadable` hard gate hard-rejects any direct attempt to enqueue one — wrapped not only at that seam but also at the live per-chunk upload seam (`chunk_processor.upload_chunk_files` and `reconcile_against_gcs`), so a raw artifact reaching any enqueue path fails loud rather than shipping silently. Cloud-bound structured data derives **only** from scrubbed exports (events JSONL, transcript, manifest), never the DB.

- **Cloud video privacy depends on the `masked_video_upload` flag:**
  - **Flag OFF (the default, and the current shipped posture): capture-time blocking is a *structural* guarantee.** For a cloud-bound recording, sensitive application windows are dropped from the recorded video *at capture time* (`RecorderPrivacyFilter`, in `screencap.enforcement`), so the sensitive pixels are **never written to disk** in the cloud-bound video and cannot leak even if every later stage fails. This is the strong guarantee and it is unchanged from prior releases.
  - **Flag ON (future, not yet enabled): cloud video is captured rich and masked *post-hoc*.** Video is captured for all destinations (rich local copy, R7), and the terminal stage produces a masked cloud copy by drawing opaque masks over sensitive-window regions using the recorded `window_geometry` timeline (`video_mask.mask_video_chunk`). This is an **operational** guarantee, weaker than capture-time blocking: it depends on geometry coverage and on the masker running correctly. It is defended by a **fail-closed three-way coverage gate** — for each chunk's frame span, the masker (a) produces an unmasked copy only when geometry *proves* no sensitive window densely covered the whole span; (b) **fails closed** (marks the chunk `FAILED`, produces no copy, blocks upload) when coverage is unprovable — any geometry-capture-failure marker in the span, zero samples, or an inter-sample gap exceeding a bounded maximum (2.0s); (c) otherwise masks conservatively (hold-and-pad + dilate so a window moving between samples is over-masked). A "did nothing" outcome on a sensitive chunk is loudly distinguished from success and fails closed; a missing classifier or a decode error also fails closed.

    Three further fail-closed guards harden this dormant ON path (SCR-126), so it can be enabled safely later: (1) an explicit **upload-seam assertion** (`upload.assert_video_masked`) applied at *every* chunk-media enqueue path — the live and terminal per-chunk seams, the reconcile re-enumeration, and the scrubbed-dir `upload_recording`/`list_recording_files` rglob — rejects any cloud `chunk_*.mp4` that is not the masker's output under `masked_video/`, so the rich capture-time source can never leave the machine even if a caller's masked-path switch regresses; (2) the coverage gate proves coverage over each chunk's **real decoded PTS extent** (derived from the chunk's own packet PTS, not a uniform per-chunk grid that can fall short of — or overshoot — the real frames), plus a fail-closed in-loop guard that refuses any frame outside the proven span, so trailing frames can never ship clear while the chunk reports `MASKED`; (3) the scrubbed-copy **reuse path and the convergence fast path are gated on masked-video provenance** (`masked_video/.masked_provenance.json` fingerprinting the source chunk bytes, the geometry timeline, the privacy policy, `pixel_ratio`, the frozen flag, and a mask-logic version), with an authoritative closed-set reconcile that purges any stale or orphaned masked copy — so a stale or under-masked copy from an earlier run (or a recording converged under older mask logic) can never be re-uploaded.

**The trade-off is explicit and accepted.** Moving cloud-video privacy from capture-time blocking (pixels never recorded) to post-hoc masking (pixels recorded, then masked, fail-closed-dependent) trades a structural guarantee for an operational one tied to STRATEGY.md's near-zero privacy-incident bar. The fail-closed coverage gate is what keeps that bar; capture-time fails safe (not recorded), post-hoc fails open (recorded; the masker must not miss) — which is why the flag defaults OFF.

**Clip-a-moment export (`screencap clip`) inherits this boundary and fails closed (SCR-219).** The video clip is trimmed from the recording's SOURCE `chunk_*.mp4` (`engine.video.export_clip` / `export_clip_video`), so in the default flag-OFF posture it carries exactly the capture-time-blocking guarantee above: sensitive windows were never written to those source chunks, so a clip — which only pulls source frames and adds nothing — can never contain them. The clip pipeline does **not** depend on `masked_video_upload`: it never enables the flag, and it never reads the post-hoc `masked_video/` copies (its non-recursive `chunk_*.mp4` glob cannot match them). When the recording's **frozen** `.recording_intent` `masked_video_upload` bit is ON — meaning capture-time blocking was disabled and the source chunks hold rich, unmasked sensitive windows — the clip **fails closed** *before reading a single chunk*: it raises a structured `masked_video_required` reason and writes no file, rather than exporting rich sensitive-window video to an external-recipient clip (KD4/KTD3). This inversion is deliberate: the post-hoc masker exists to make flag-ON *cloud uploads* safe, but a local clip destined for hand-off is refused outright on a flag-ON recording rather than routed through post-hoc masking. The invariant is CI-guarded, Vision-free, in the privacy lane (`tests/test_clip_privacy_parity.py`).

**Enabling `masked_video_upload` remains gated on the prerequisite below** (so the flag MUST stay OFF until it lands). Two earlier prerequisites are now met: the **live-upload cutover landed** (SCR-125 — the live per-chunk cloud path masks through the shared seam before upload, so flag-ON no longer ships rich unmasked video via the live path), and the **fail-open hardening of the dormant ON path landed** (SCR-126 — the upload-seam assertion, real-extent coverage, and reuse/convergence provenance described above). The capture-time blocking removal (`block_video`) is gated behind this same flag, so the default-OFF posture keeps the structural guarantee intact.

1. **Consent-surface reconciliation (outstanding).** The native redaction-review window still labels video "local-only, not uploaded." That surface must be updated to show that masked video uploads before any operator can meaningfully consent to it. While the flag is OFF that label is accurate (masked video does not upload), so this reconciliation lands with the flag flip, not before.

## Masked frames to a connected Intelligence model (SCR-272)

A cloud-bound Intelligence task — a summary/title or a recall answer that has already resolved to the user's connected cloud model — can optionally carry **best-effort masked screen frames** as multimodal evidence, governed by a single config flag, `frames_cloud_consent` (`SCREENCAP_FRAMES_CLOUD_CONSENT`, **default `false`**). This is an **independent, opt-in** consent: it is not implied by connecting a provider, and not by the summary/recall cloud-consent rows (which default on) — AE1. Two facts define the boundary, and — unlike the `masked_video_upload` gate above — the two halves have deliberately **different** strengths:

- **The blocked-app boundary is STRUCTURAL and provable, fail-closed.** Frames are produced only by `screencap.segmentation.frame_egress.produce_egress_frames`, the **sole** blessed constructor of a `MaskedFrame(masked=True)` (AST-guarded in `tests/segmentation/test_generation.py`; that `masked=True` stamp is the provenance the provider seam's `verify_masked_frames` fail-closed guard checks before any frame reaches a provider). Every candidate frame is tested against the recording's re-derived **ALLOW-only** skip set via `frame_blocked.build_is_blocked` — the same `derive_skip_intervals(require_canonical=True)` machinery `frame.nearest` uses — and a frame is emitted **only** when its ALLOW eligibility was *positively* derived. Any derivation failure (missing/partial `recording.db`, a partial canonical read, a broken privacy config) maps to an **all-blocked sentinel**, so **zero** frames leave (AE4/R10); a frame overlapping a blocked-app interval is excluded (AE2/R8). Frames from EXCLUDE / MASK_WINDOW / secure-field / masked apps are therefore never eligible — a structural guarantee, the same class as capture-time blocking above.

- **Residual within-frame masking is BEST-EFFORT OCR — NOT a coverage guarantee.** For a surviving ALLOW frame, the still is decrypted to RAM (never a decrypt-to-temp), OCR'd (Apple Vision + the regex/secrets/PII pipeline), and detected secret/PII regions are painted out in-memory before the bytes leave; the on-disk `screenshots/*.jpg` is never mutated (R9). This is a defence-in-depth pass, **not** a proof — the detector set is finite, OCR can misread, and unrecognized sensitive content can survive. When the OCR pipeline is unavailable the pass is **skipped** (the frame still leaves — the structural boundary is the guarantee), and any raise while loading/masking a frame **drops that one frame** (never emitted raw). **This is the key distinction from `masked_video_upload`:** that flag's cloud-video path is defended by a *geometry-based, provable, fail-closed coverage gate* (a chunk ships only when geometry proves no sensitive window covered its whole span); frame egress has **no** equivalent within-frame coverage proof — its provable guarantee is the *which-app* blocked-app boundary, while *within-frame* content masking is best-effort only. Operators and any consent copy must not describe the within-frame mask as a guarantee; the honest split (blocked-app = provable, within-frame = best-effort) is stated at the decision point in the Intelligence pane.

- **Frames ride only where a cloud-bound task's text already egresses.** Frames are never a standalone cloud task — `ConsentPolicy.resolve(TaskKind.FRAMES)` returns `NEVER` in every configuration (R9). `frames_may_attach(policy, resolved_target)` (the only frame-egress gate, separate from `resolve`) returns true only when **all** hold: the host task already resolved to `ExecutionTarget.CLOUD` (a summary/recall in its on-device-unavailable cloud fallback), `frames_cloud_consent` is set, and a `cloud_provider` is configured. So enabling the opt-in never opens a **new** egress destination — it enriches a task whose already-stripped text was leaving to that same connected model — and nothing is sent while a task runs on-device or while no cloud model is connected. Recall additionally scopes frames to the stills nearest the *retrieved* snippet timestamps (`only_timestamps`), never the whole answered window; near-duplicate frames are deduped and the per-window survivor count is hard-capped (deterministic).

**Default OFF; the consent surface is honest and state-keyed.** The macOS Intelligence pane surfaces `frames_cloud_consent` as an interactive, **default-off** toggle gated behind a **decision-time disclosure** (the app-picker consequences-dialog pattern) that names exactly what leaves: best-effort masked frames of ALLOW-only activity, sent to the connected model, never raw pixels, blocked apps stripped first. The pane's per-task captions and the trust footer are **state-keyed** on the toggle — the absolute "never screen images" claim holds only while the toggle is OFF; when ON, the copy names that masked frames may be sent (U6/U7). The redaction-review window's "local-only, not uploaded" video label is **unaffected** by this flag: the navigation video is never a frame-egress candidate (the producer reads the flat `screenshots/*.jpg`, not the `.mp4`), so that label stays accurate in both toggle states — distinct from the `masked_video_upload` reconciliation above, whose flip *does* make the video leave.

## User allow-list authority over the privacy matrix (SCR-235)

The (context × mode) privacy matrix is a set of **suggested defaults**, not a ceiling on user consent. A **confirmed allow-list entry** — a bundle present in both `[privacy].allow_apps` and `[privacy].confirmed_allow_apps` — is authoritative over the matrix **in every privacy mode**, including for classes the matrix excludes (password managers, banking, auth/payment flows). This deliberately replaced the earlier matrix-strictness floor, which prevented `allow_apps` from loosening `EXCLUDE`/`MASK_WINDOW`/`TEXT_REDACT`: now that the product has real per-app consent surfaces, the user's explicit, confirmed choice wins.

- **Consent is gated where it is risky.** Allow-listing a class the matrix excludes in *any* mode (the matrix-derived `CONFIRMATION_REQUIRED_CLASSES`: password manager, banking, auth flow, payment flow) requires an explicit confirmation — the `--confirm-sensitive` flag on the CLI, or the app-picker's consequences dialog, which names the full cascade at decision time: raw capture, keystrokes kept, searchable index (including already-recorded frames once indexing re-runs), and inclusion in cloud copies when a recording is cloud-destined. Mask-class apps (chat, email, browsers, terminals) confirm silently on add — a new deliberate add is what distinguishes them from legacy entries. The confirmation dialog's consequence list and this paragraph are kept in sync.
- **Legacy entries keep the floor.** An `allow_apps` entry with no matching `confirmed_allow_apps` entry (pre-SCR-235 configs, the setup wizard's silent auto-allows, hand edits) keeps the old matrix-strictness floor, preserving the Unit-7a migration guarantee: a stale allow entry can never silently re-enable raw capture under tightened defaults. Confirming through the UI/CLI is the upgrade path. The setup wizard never silently auto-allows a confirmation-required app, and its silent auto-allows are written as legacy (unconfirmed) entries — only explicit per-app choices in the review flow confirm, and for confirmation-required classes the wizard shows the same consequence confirmation as the CLI and app-picker before writing the confirmed entry (declining keeps the app blocked).
- **Precedence.** Explicit deny (`exclude_apps`) beats everything; the user's own domain/title mask rules outrank any allow (a finer-grained user rule holds inside apps the user allowed); then the confirmed allow; then the legacy floor; then the matrix default. One carve-out: within a confirmed-allowed **browser**, a window the classifier refines to a confirmation-required context (a banking/auth/payment page) keeps the matrix action — app-level consent does not extend to arbitrary sensitive content a browser can host.
- **The confirmed allow cascades everywhere, including cloud.** A confirmed app evaluates `ALLOW`, so it is captured raw (screenshots, keystrokes, video), OCR-indexed, resolvable via `frame.nearest`, and included in cloud-bound copies. The two PUBLIC-forcing cloud surfaces (the cloud window filter and the background-window masking evaluator) restrict the allow set to **confirmed entries only** — replacing the old strip-to-empty — so legacy entries still never loosen cloud posture.
- **Retroactive exposure is part of the consented cascade.** Frame resolution and the content-index backfill re-derive the skip set from *live* settings, so confirming a previously mask-class app makes its already-on-disk local frames indexable/servable going forward (nothing re-indexes automatically, and the purge path is unchanged — there is no un-purge). Previously `EXCLUDE`-class apps have no pre-confirmation frames on disk to expose. This is disclosed in the confirmation dialog.
- **Menu-bar runtime overrides are a pre-existing parallel path, unchanged.** The session-scoped menu-bar toggle (`.menubar_overrides.json` / the override queue) can already grant `allow` to any bundle — including confirmation-required classes — without the confirmation gate. It is out of scope for SCR-235: it remains session-scoped, never writes `confirmed_allow_apps`, and stays stripped from cloud-bound filtering, so the trust statement above should be read as governing the *persistent* config surfaces.

## On-screen content index + MCP query surface (SCR-118)

ScreenCap can expose a queryable retrieval surface over recordings to a local agent: a `screencap mcp` stdio server forwards to three read-only daemon verbs (`/v0/content.search`, `/v0/transcript.search`, `/v0/timeline.query`) that return **text snippets + `(recording, timestamp)` pointers — never frame pixels or file paths**. This sits entirely inside the same-EUID trust boundary above; it adds no network surface and no per-caller auth (the `mcp` provenance label remains advisory and gates nothing). Three facts define its privacy posture:

- **`~/.screencap/content_index.db` is a new at-rest store of the same sensitivity class as recordings — local-only, by rule.** It holds on-screen text recognized by an OCR pass that runs during chunk processing (config flag `content_index_enabled` / `SCREENCAP_CONTENT_INDEX`, **default off**). It is created with hardened at-rest perms — `0o600` for the DB and its `-wal`/`-shm` sidecars, `0o700` parent, with a symlink guard before connect (not relying on umask), matching the `auto-serve.log` precedent — and it lives **outside** the `recordings/` tree, so it is never part of any uploaded set (like `recording.db`). Cloud structured data still derives only from scrubbed exports; the index never leaves the machine.

- **Narrowed R7: the index holds post-OCR text from *local, unmasked* screenshots, restricted to policy-`ALLOW` frames.** The live recorder writes screenshots to a flat `<capture_dir>/screenshots/` and **never masks them in place** — masking only ever runs over a `<name>-scrubbed` *copy* at the terminal/cloud stage (and only for cloud/both destinations). So the index OCRs unmasked pixels. This is acceptable *only* because the index is the same sensitivity class as those local screenshots, which a same-EUID process can already read directly — indexing them creates **no new cloud exposure and no new cross-EUID exposure**. The two guarantees that carry the privacy weight are upheld: (1) the store is **never uploaded**, and (2) it is **purged on destroy** — `content_index.delete_recording_interval` on a retroactive "disable this app" (converting the scrub worker's float-seconds intervals, including the trailing `+inf`, to a floor/ceil-widened ms purge), and `content_index.delete_recording` for a full recording delete (a ready API; no in-app full-delete command exists yet, so external `rm` orphans are deferred like backfill — deletion of media via `stub_recording` intentionally does **not** purge, so a stubbed recording stays queryable). **The index pass skips every frame the policy flagged for *any* masking/redaction action** (`EXCLUDE`, `MASK_WINDOW`, `MASK_REGION`, `TEXT_REDACT`, `OCR_FALLBACK` — the full `SCRUB_BLOCK_ACTIONS` set carried on the scrub result's `blocked_intervals`), so the index holds only `ALLOW`-classified on-screen text — **never more than the scrubbed cloud copy's screenshots would**. Focused password fields, excluded apps, and masked windows (banking / email / chat) are therefore never indexed. Note that since SCR-235, `ALLOW` includes apps the user **confirm-allowed** over the matrix defaults — their on-screen text is indexed by explicit consent (see [User allow-list authority](#user-allow-list-authority-over-the-privacy-matrix-scr-235)); the invariant is unchanged in form: the index never holds more than the policy's `ALLOW` set.

  The index pass is **strictly fail-open** — any OCR/index error logs and continues; it never changes a chunk's status, upload, or deletion (redaction output is byte-identical with indexing on or off), and it bails on `_stop_event` and a wall-clock budget so a slow/wedged OCR engine can never sit in front of a chunk's upload. Each chunk's write **replaces the whole chunk time-range** (not just the surviving frames), so a `--force`/reconcile re-process under a tighter policy drops now-skipped frames' stale rows rather than leaving them. **An inline index write and a concurrent retroactive-disable purge are serialized by a shared write lock** (`content_index.content_index_write_lock` — an in-process lock plus a best-effort cross-process `fcntl.flock`, mirroring `terminal_lock`), held across the inline OCR-read-and-write and across the purge. Because the scrub worker unlinks the underlying screenshots *before* taking that lock, the two possible orderings both converge to purged — write-then-purge deletes the just-written rows; purge-then-write re-reads an already-emptied disk and indexes nothing — so text from a just-disabled app can never be resurrected in the store (SCR-134). One accepted v1 limitation remains: re-scrubbing an already-captured recording with a *stricter* policy via `screencap scrub` does not retro-update the index (the index reflects the policy in effect at capture time); the remedy is delete-and-re-record or a future backfill.

- **The query verbs are read-only and unaudited, and keep the daemon alive via a held subscription — not by counting as activity.** Like `recording.list`, the three query verbs are not audit-logged. They are deliberately **excluded from `_idle_shutdown._ACTIVITY_PATHS`**, so cron-style polling cannot pin an auto-spawned daemon open forever. Instead the MCP server holds one `/v0/events` subscription open for the agent session — the existing `subscriber_count() > 0` busy path — which keeps the daemon alive during a conversation and self-clears on disconnect (the daemon idle-shuts-down ~600s after the session ends). Inputs are validated at the daemon boundary: the caller-supplied `recording` filter is routed through `validate_recording_name` / `resolve_recording_dir` (traversal-safe), the FTS `MATCH` is bound and phrase-escaped (operators/column-filters stay literal), time ranges are bounded, and the per-query recordings/limit caps are enforced at the handler so a direct UDS caller cannot drive an unbounded cross-recording scan. The `timeline.query` stream **omits `browser_url` from its output** (captured pre-scrubber, can carry OAuth codes / session tokens) — see the SCR-179 note below for how it is read internally as a domain *filter* predicate without entering a result row; transcript search reads only the strict scrubbed `transcript_<NNNN>.txt` (never the rich per-word `.json`, never an appended `*.txt.scrub_failed`). Soft-fail diagnostics carry only an exception class name / `index_state` enum, never a path or raw message.

**Day-timeline provenance fields (`/v0/timeline.day`, SCR-277) stay inside the same boundary.** The app-facing day surface additively carries a per-recording `end_status` (`live`/`clean`/`interrupted`/`unknown`, resolved from the recording's own stop artifacts) and `purged` spans whose optional identity (`bundle_id`/`app_name`/`root_domain`) is joined from the local `purged_interval` table and the per-recording `.menubar_disable_log.jsonl` audit log, plus top-level `store_mounted` and `coverage_complete` flags (the latter only signals that an unreadable `recording.db` kept a recording off the day — a boolean, carrying no recording identity). This exposes exactly the sensitivity class a same-EUID process already reads directly from `recording.db` and the disable log — no new at-rest store, no new cross-EUID exposure. The fields travel only over the same-EUID UNIX socket, are never uploaded (the dotfile-sidecar and `recording.db` upload exclusions are untouched), and the verb is **not** part of the MCP tool surface — an agent session cannot reach the purge-identity join through `screencap mcp`. The identity join degrades to identity-free on any ambiguity (never a guessed identity, R7), and `purged` spans are kept distinct from `blocked_proven` so retroactive deletion is never presented as proven capture-time masking.

## Nearest-frame resolution primitive (SCR-186)

`/v0/frame.nearest` (and the `resolve_frame` MCP tool) closes a usability gap in the pointer-only query surface above: an agent that holds a `(recording, timestamp_ms)` search pointer has no supported way to learn *which local screenshot was on screen at that moment* without re-implementing the `{epoch:.6f}.jpg` listing + millisecond + staleness logic. The verb resolves that pointer to the nearest on-disk screenshot **stem** (e.g. `1719400010.000000`) plus a signed `delta_ms`. It preserves the same-EUID + pointer-only posture of the SCR-118 verbs:

- **No image bytes, no path — a stem only (R8).** The response carries a bare filename stem, never a path or pixels. The agent expands it to `~/.screencap/recordings/<recording>/screenshots/<stem>.jpg` and reads it with the same-EUID filesystem access it already has; the daemon is not in the byte path. Withholding the thumbnail bytes from the wire is the line this primitive deliberately does not cross — the gap it fills is the *resolution*, not the image.

- **ALLOW-only at the resolution layer, fail-closed.** Unlike the Swift app-side `RecordingFrameIndex` (which surfaces every local frame for the operator's *own* on-screen viewing under the same-EUID boundary), this is an **agent-facing** surface, so it applies the **same `SCRUB_BLOCK_ACTIONS` skip the content index applies**: a frame the policy flagged for any masking/redaction action is never selected — a masked moment resolves to the nearest `ALLOW` frame, or to a `null` miss. This holds the content index's ALLOW-only invariant at the resolution layer so an agent reasoning "the daemon handed me this stem, so it's safe to surface" is never pointed at a masked frame. The blocked geometry is **re-derived per request** from the recording's intact local `recording.db` by reusing the SCR-178 backfill skip-interval logic (`backfill.skip_intervals` + `scrubber.find_blocked_interval`), so the resolve-time skip can never drift from the index-time skip. The derivation **fails closed** on the cases it can detect: a missing / unreadable `recording.db` flags *every* frame (no covering window event → every frame is an uncovered gap), and any error building or merging the predicate falls back to an all-blocked sentinel — so the verb returns a miss rather than risk surfacing a sensitive frame (the one place the system is deliberately fail-*closed*: a resolution that could point at a masked frame is worse than a null). It inherits the backfill's **superset** derivation, which over-skips on coverage gaps and NULL-column classification ambiguity. The earlier inherited residual — `build_scrub_context` returns an *empty* canonical block set on a partial internal read error without raising, indistinguishable at this layer from a legitimately all-`ALLOW` recording, so a narrow partial-`recording.db`-read could under-block — is now **closed (SCR-198)**: `build_scrub_context` carries a `canonical_ok` success signal (set `False` on any read failure that empties/partials the canonical set), `derive_skip_intervals(require_canonical=True)` raises `CanonicalDerivationError` when that signal is false, and `frame_blocked.build_is_blocked` maps the raise to the all-blocked sentinel — so a partial canonical read now fails closed (a miss) rather than under-blocking. The fail-*open* backfill path omits `require_canonical` and is unchanged. Inputs are validated and bounded at the boundary (`validate_recording_name`; `timestamp_ms` / `staleness_cap_ms` capped) and the verb stays out of `_ACTIVITY_PATHS`.

- **Transcript timing adds no new exposure.** `transcript.search` hits are additively enriched with `timestamp_ms` (the chunk's `chunk_start`), `timestamp_granularity: "chunk"`, and `chunk_duration_ms`, read from the local-only per-chunk manifest (counts + timing + blocked intervals only — no OCR/URL content). This is wall-clock timing of the same sensitivity class a same-EUID process already reads off disk, exposed so a chunk-granular transcript pointer is resolvable; the rich per-word `transcript_*.json` (an R7 leak) is still never read.

## Search-by-default guardrails: encrypted recall corpus + present-user gating

Search / agent-queryable memory ships **on by default** (behind a readiness gate + a disclosure), which is only defensible because the materialized recall corpus — the flat `screenshots/*.jpg`, `content_index.db`, and inline screenshot blobs in `recording.db` — is protected by four guardrails. This is a hardening of the SCR-118 boundary above, not a widening of it: everything here stays inside the same-EUID boundary and adds no network surface.

- **At-rest encryption (R3).** Persisted stills are AES-256-GCM (`corpus_crypto` — nonce + tag framed behind a `SCE1` magic, written as `screenshots/<ts>.jpg.enc`), the content index is SQLCipher page-encrypted (`content_index.db`, FTS5 intact), and `png_data` blobs in `recording.db` are encrypted with the same key. Each ciphertext's AAD binds `(recording-dir-name, filename)` so a still cannot be silently swapped across recordings. The **corpus key** lives on the data-protection Keychain in the shared access group `2A8S6MV8DZ.com.screencap.shared`, so the entitled app daemon and bundled CLI read it without a prompt; **un-entitled binaries** (pip/pyenv CLI, Debug builds) get `errSecMissingEntitlement` and fall back to the legacy `keyring` tier — a separate key for that install. The daemon-spawned **engine subprocess** (a different Keychain ACL identity) can't read the group, so the daemon writes the key to a `0600` file and passes only its *path* via `SCREENCAP_CORPUS_KEY_FILE` (never argv/config — `ps`-visible), mirroring the ID-token channel. **Key loss = corpus loss** (stills + index become unreadable) is accepted by design: the corpus is derived data; the **video is the untouched source of truth** and stays readable. Losing the key never loses a recording.

- **Secrets-only scrub before indexing (R1), and its limits.** At index time each still is decrypted to RAM (never a decrypt-to-temp — the OCR reads in-memory bytes), OCR'd, and its detected secret/PII spans (a *lighter* profile than the upload masker: `RegexDetector` + `DetectSecretsDetector` + an EMAIL regex — deliberately **no** PERSON NER and **no** structural pane/window masks, which would destroy search recall) are painted out of the persisted still and replaced with `<TYPE>` tags in the indexed text. **Under-detection is inherent**: the detector set is finite, OCR can misread, and a secret with no regex/entropy signature evades it — the scrub *reduces* exposure, it cannot *eliminate* it. The residual protection is the other three guardrails (encryption + present-user gating + the upstream ALLOW-only blocked-frame skip, which is unchanged and still excludes secure fields / masked / excluded apps). The scrub is **fail-closed on protection**: if the detection pipeline can't be built, the pass indexes *nothing* (never raw, unredacted text) and the chunk is left for a later processing pass to retry — R1 never silently degrades to an unredacted index.

- **Retention bound (R2).** The `screenshots/` dir is age/size-capped (default 30 days once guardrails are on), enforced both during recording and by a not-auth-gated periodic daemon sweep; an evicted frame's content-index rows are purged with it (retention forgets the frame, pixels *and* text). The bound never evicts a frame the indexer hasn't reached yet (don't race the indexer).

- **Present-user gating is app-display-only; agents ride the same-EUID bar (OQ3).** User-facing corpus *display* in the app (search-result stills, the truth pane, full-size stills) is gated behind Touch ID / `LocalAuthentication` with a session grace window — a proof-of-presence check on *viewing*, modeled on the shipped Windows Recall posture. Background daemon **indexing is not gated** (a daemon cannot prompt; capture/index continues unattended). Agent/MCP access is **not** present-user gated: a headless agent can't satisfy a biometric prompt, and — critically — the corpus key sits behind the shared-group **entitlement**, so an arbitrary same-EUID process *cannot* read a still directly. That makes the daemon's `frame.read` verb a real boundary, not just defense-in-depth. `frame.read` (KTD6) decrypt-and-serves a still only when it is an **ALLOW** frame (fail-closed on masked/indeterminate) **and** its chunk has actually been secrets-scrubbed (`scrub_state` per-chunk marker — a frame captured but not yet index-scrubbed is refused, so the capture→index window never leaks), **size-capped**, and **audit-logged per invocation** (peer + ok/blocked/error via `audit_log.record_verb`). `frame.nearest` signals `encrypted: true` so the agent calls `frame.read` instead of reading the path. Same-EUID + ALLOW + scrubbed-chunk + audit is the deliberate trust bar for agents; a stronger per-agent present-user check was considered and rejected (it can't apply to headless/cron agents and diverges from the daemon's same-EUID model).

- **The default flip is a readiness gate, and nothing changes what uploads (R7/R8).** The default never flips for a user who hasn't seen the disclosure. At `recording.start` a pure gate resolves stills capture: an explicit opt-out always wins; an explicit opt-in is clamped OFF when encryption is required but its key/scrub aren't ready; an unset default turns ON only when the corpus is encrypted **and** the key, scrub pipeline, this recording's scrub, the retention bound, and the acknowledged-disclosure marker are all present and consent wasn't declined — otherwise the recording proceeds video-only with a logged reason (R8 fail-closed). The upload seam is untouched (R7): the `<name>-scrubbed` cloud copy is produced **decrypted + upload-masked** exactly as before (encrypted stills are decrypted to plaintext masked JPEGs at copy time, or dropped fail-closed if un-decryptable), so the uploaded artifact set is byte-shape-identical and `recording.db` remains local-only. Existing plaintext corpora are migrated to the encrypted form in one idempotent, resumable, interruption-safe pass at flip time; the local-only `.scrub_state.json` marker is excluded from upload and the cloud copytree.

## At-rest encryption: the on-disk vault container (SCR-258)

The optional at-rest corpus encryption above (R3) covers only the recall corpus (stills, index, `png_data`) and only when Search guardrails are on. The **vault container** is the whole-library at-rest layer: the entire local recording data plane — the recordings tree (`recording.db` with wal/shm, screenshots, video chunks, transcripts, exports), the content index, and the backfill ledger — lives inside an app-managed encrypted disk image (an AES-256 sparse bundle at `~/.screencap/store.sparsebundle`, APFS inside), mounted transparently at the recordings directory so every existing consumer reads it unchanged while mounted. On top of that always-on baseline sits a manual, present-user-gated **Lock**. It is gated by `container_enabled` (`SCREENCAP_CONTAINER_ENABLED` / config `container_enabled`), **default on** (the SCR-258 shipped posture — with no installed base pre-launch there is nothing to migrate, so the container ships from the first recording), so the unconditional claim below applies to every new install; the flag can still be turned off on a fresh, no-bundle install (`SCREENCAP_RECORDINGS_DIR` remains the plaintext dev/test seam). The corpus crypto (R3) is unchanged and composes *inside* the container (KTD-21): it still protects against an un-entitled same-EUID reader while the store is mounted, the one case the container cannot cover. This section states the boundary as plainly as the same-EUID posture above demands.

- **What the container protects (at rest, sealed, and off-machine).** The on-disk sparse bundle is ciphertext at all times. A backup tool that copies the raw bundle — including Time Machine copying individual bands — captures only opaque ciphertext that yields no recording content without the Keychain key; the same holds for a copied bundle, a disk image, or the drive of a **FileVault-off** machine. Another local macOS user cannot read the mounted volume (the mountpoint and bundle stay under the `0o700` home). And an explicit **Lock** flips the store into a **sealed** (unmounted, ciphertext-only) state that survives daemon restarts and reboots until a present-user unlock — the deliberate stepped-away / lent-machine / travel case. Lock is a *manual* action only: there are no auto-lock triggers (locking unmounts, and unmounting stops recording, so any idle/screen-lock auto-lock would kill all-day background capture); Lock stops any active recording cleanly at a chunk boundary before sealing, and unlock never auto-resumes recording.

- **What it does NOT protect: a live same-EUID process while mounted.** The all-day LaunchAgent must mount the store with no user present, so the container key is **headlessly readable from the Keychain by product necessity**. Any process running as your effective UID can therefore read that key and attach the bundle directly, or read the mounted plaintext, exactly as it can already read `~/.screencap/recordings/` today. The container raises the at-rest and off-machine bar; it does **not** turn the machine into a sandbox against same-user code. **The present-user (Touch ID) unlock gate is a UX gate over that same-EUID posture, not a cryptographic boundary** (R14 / KTD-16): it defends the casual-access case (someone else at your unlocked machine, or a stepped-away sealed store), not a local attacker with your UID — who can delete the run-dir sealed sentinel or read the key and attach without ever satisfying Touch ID. We state this rather than imply the gate is stronger than it is.

- **Split custody: only entitled binaries are supported vault consumers (KTD-22).** The container key lives in the same device-local shared Keychain access group (`2A8S6MV8DZ.com.screencap.shared`, `kSecAttrSynchronizable=false` — never iCloud-synced) as the corpus and auth keys. Entitled binaries carrying the `keychain-access-groups` entitlement (the app's embedded daemon + bundled CLI, one code identity) read it without a prompt; an **un-entitled** binary (a pip/pyenv terminal CLI, a Debug build) gets `errSecMissingEntitlement` and **cannot** read the group key, so it cannot mount the shared-group store. A pip- or dev-source daemon is therefore an **unsupported** vault consumer — documented, not a bug. Because a bundle-exists-but-key-unreadable state is otherwise ambiguous, the hard-stop guidance distinguishes **"no key in any channel"** (genuine key loss → data unrecoverable) from **"the key is present in the shared group but this binary lacks the entitlement to read it"** (an entitlement mismatch that names the entitled app/CLI as the fix). The latter is **not** data loss, and the diagnosis says so instead of raising a false loss alarm.

- **Key loss is unrecoverable, by design (R10).** There is no ScreenCap-built escrow or key recovery in v1 (mirroring the cloud-KEK stance for SCR-252): if the Keychain entry for the container key is lost, every recording inside the container is permanently undecryptable. A machine **restored without the login/Keychain** — e.g. a selective `~/.screencap`-only restore that carries the bundle but not the key — leaves the store as intact ciphertext that nonetheless cannot be opened. Both the app and this document state this plainly; nothing on disk is ever destroyed to reach this state, and there is never a silent fallback to plaintext recording when the key or unlock is unavailable.

- **Downgrade to plaintext is unsupported.** Once a container exists, setting `container_enabled=false` does **not** serve the library as plaintext: the daemon surfaces a typed **"downgrade unsupported"** state rather than mounting or mkdir-ing a plaintext directory at the mountpoint. The off value is honored only on a **fresh, no-bundle install** (and under the `SCREENCAP_RECORDINGS_DIR` dev/test seam). A genuinely pre-container binary reads the bundle-bearing install as an **absent** store (it never looks for a sparse bundle) — so nothing is destroyed, but its recordings do not appear until an up-to-date, entitled binary mounts the container. Reverse migration / decrypt-in-place is deferred.

- **Claim boundaries (what is deliberately outside the at-rest claim).**
  - **Custom recordings locations bypass the container by design.** An install already on a custom `recordings_dir` (config) or with `SCREENCAP_RECORDINGS_DIR` set is **plaintext** and **outside** the at-rest claim: it is excluded from the migration prompt and never silently relocated. "Change storage location" for a vault install relocates the *encrypted bundle* itself (R16); the env/custom-dir bypass stays plaintext.
  - **The daemon run-dir stays plaintext, outside the container (R4).** The UNIX socket, daemon logs, and the audit log under `~/.screencap/run/` are not inside the bundle and are not encrypted. Treat them (and recording filenames/durations) as the same sensitivity class as the recordings, per "Threats out of scope" below.
  - **QuickLook host-cache thumbnails are a documented residual.** macOS may cache thumbnails of recording artifacts in the per-user QuickLook cache outside the bundle; these are host-side, same-EUID-readable, and not covered by the container.

- **Migrated-install remanence (upgraders only).** Migration copy-verifies each recording into the container and deletes the plaintext originals only in a post-cutover sweep. After the sweep the *live* library is fully inside the container, but two residuals remain and are disclosed: (1) the deleted plaintext bytes may **persist in the host volume's free space and in APFS local snapshots** until they are overwritten or the snapshots expire — **FileVault covers that free-space residual** (a strong reason to run FileVault, which the app warns about when off, R15); (2) any **backup taken before migration remains plaintext forever** — the container cannot reach back and re-encrypt an existing Time Machine snapshot. Neither residual exists for a fresh default-on install, which is ciphertext from the first recording.

- **MCP mid-read residual (a documented R6 boundary, not a silent failure).** The pointer-only MCP surface hands an agent a screenshot *stem* which it reads off disk with its own same-EUID access — the daemon is not in the byte path. If a **Lock** force-detaches the volume in the narrow window between resolving a stem and the agent opening it, that read can fail mid-stream (raw EIO/ENOENT). This is **documented**, not hidden: Lock emits a pre-detach `store_locking` signal so in-app readers release handles first, and the app maps a mid-read stem failure to a `store_state` re-check that renders the explicit **locked** state rather than a corruption-looking error. A headless agent simply sees the read fail and can re-query, at which point the read verbs return the typed `store_state=locked` as data.

- **Which binaries are supported vault consumers.** The **app's embedded daemon and the bundled CLI it ships** (one entitled code identity) are the supported consumers of a shared-group container. A pip/pyenv CLI or a Debug/dev-source daemon is un-entitled and **unsupported** for the vault (it gets the entitlement-mismatch diagnosis above); it continues to work normally on a plaintext, no-container install.

## Range delete: irreversible local removal (U8, KTD-3)

The day surface offers a **range delete** — select a time range and remove that range's footage from this Mac. It is a store-touching mutation driven by a Supervisor-style daemon job (`/v0/delete.start` with a `dry_run` preview, `/v0/delete.status`, `/v0/delete.cancel`). Its data-lifecycle posture:

- **Local-only in v1.** The delete removes the range's footage from **this Mac only** — playback, screenshots, transcripts, the content index, `tasks.json`, and every agent retrieval path (`content.search`, `transcript.search`, `timeline.query`, `frame.nearest`). It does **not** propagate to any cloud copy; the confirm and hover copy say "removed from this Mac," and cloud propagation is deferred follow-up work (R20). The ledger's cloud floor (fresh-remote-re-confirm before deleting an uploaded chunk) is untouched.

- **`recording.db` is never deleted — a tombstone rule.** Range delete removes *rows inside* `recording.db` (the in-range `window_event`/`action_event`/`screenshot`/`window_geometry` rows) but never the file itself, so a fully-deleted recording leaves a tombstone directory preserving provenance (the `purged_interval` span + the `USER_DELETED` ledger rows). The row deletes, the `origin='user'` `purged_interval` write, and the `pipeline_chunk_state → USER_DELETED` transition all commit in **one `BEGIN IMMEDIATE` transaction** (mirroring `scrub_worker`'s crash-consistency), so a crash can never leave rows deleted but the span / ledger state unrecorded.

- **`purged_interval` gains an additive `origin` column.** `'user'` marks an explicit range delete ("removed by you"); `'policy'` marks the retroactive-disable purge ("removed by your rules"); a **NULL/absent origin classifies as `policy`** (every pre-migration purge was policy-driven) in both `day_segments` and `backfill.skip_intervals`. The two are rendered as distinct honest states on `timeline.day` (never conflated with each other or with proven capture-time masking), and `skip_intervals` treats a user-deleted span as its **own fail-closed category** so `frame.nearest`/backfill degrade honestly (the footage is gone) rather than pointing at a hole.

- **The full artifact set is removed, including the reuse copy.** Beyond the chunk media (mp4/audio/events/manifest) the delete unlinks the covered chunks' screenshots, the per-chunk `transcript_<idx>.txt`/`.json`, and **regenerates the bare whole-recording `transcript.txt` from surviving chunks** (deleting it when none survive) — the bare transcript spans every chunk and is grepped directly by `transcript.search`. It also purges the same range from the **`<name>-scrubbed` sibling** (a persistent reuse cache `_iter_recording_dirs` walks, so leaving it would let deleted speech survive `transcript.search`). The `USER_DELETED` ledger state is counted "satisfied by deletion" by the terminal-stage completeness sentinel, skipped by the stage runner, and ignored by eviction — so deleting a not-yet-uploaded chunk in a cloud recording converges instead of stranding the sentinel forever. A user delete deliberately **overrides** kept-task-span retention protection (explicit intent wins); surviving clips are never cascaded and are disclosed at confirm time so "removed from this Mac" is never silently false.

- **Crash reconciliation completes an interrupted unlink.** The on-disk unlink runs *after* the transaction commits; a crash in between is completed by a reconciliation pass that runs **on daemon start and at every delete-job start** (mirroring the terminal stage's reconcile-on-entry). It re-scans the `USER_DELETED` ledger rows + `origin='user'` `purged_interval` spans against on-disk artifacts under the per-recording flock and finishes any outstanding unlink — so "removed by you" bytes can never survive a crash. It is idempotent (a completed delete re-runs as a no-op).

- **Human-only by design — a tool-surface control, not a socket boundary.** Range delete is **never exposed as an MCP tool** (R18), closing the prompt-injection → data-destruction channel at the tool surface. The `delete.*` daemon verbs, however, remain reachable by **any same-EUID process** exactly like every other verb (the daemon's authentication boundary is same-EUID + filesystem permissions, per the top of this document). The human-only guarantee is therefore a tool-surface control, **not** a claim that the verb is unreachable; that residual same-EUID channel is documented, not closed. `delete.start` is audit-logged per invocation (peer PID/binary, requested range, outcome) via `audit_log.record_verb`; progress events are recording-name-free (R9).

- **Unlinked bytes persist in the sparsebundle until compaction.** When the recordings tree lives inside the on-disk vault container, unlinking a file frees space inside the mounted APFS filesystem but does **not** immediately shrink the backing `store.sparsebundle` bands on the host disk. The removed bytes remain in unreferenced bands until `hdiutil compact` reclaims them (the container module's compact seam) — a documented at-rest residual, the same posture as any delete inside a sparse bundle, not a leak of queryable data (the filesystem entry is gone; only unreferenced blocks remain until compaction).

## Clips store: durable, retention-exempt local artifacts (U10, KTD-8)

Clipping a range produces a durable mp4 in a **dot-prefixed reserved directory** (`<recordings>/.clips/`) with a JSON catalog, inside the mounted vault (sealed by Lock, hardened `0o700`/`0o600`). The recordings-tree enumerators (`catalog.list_recordings`, `backfill/engine.py`, `retention_sweep`, `upload`) skip it by the `.store/` dot-prefix convention. Its trust-boundary posture:

- **Retention-exempt and upload-excluded.** Clips are never evicted by retention (they are deliberately-kept artifacts) and never uploaded (`.clips/` is outside `upload.list_recording_files`). They are the one durable, **externally shareable** at-rest artifact the day surface produces — Share and "Export a copy" move the mp4 off-machine at the user's initiative.

- **`clip.create` is the only MCP-exposed mutation; `clip.delete` is human-only at the tool surface.** `create_clip` is exposed to agents (additive, reversible). `clip.delete` (destructive) is **never** an MCP tool (R18), for the same prompt-injection → data-destruction reason as range delete. As with the `delete.*` verbs, the `clip.*` daemon verbs remain reachable by **any same-EUID process** — the human-only guarantee is a tool-surface control, not a socket boundary — and `clip.delete` is audit-logged per invocation.

- **`clip.create` fails closed on a policy-purged range.** Before cutting, it reads the recording's `purged_interval` spans and **refuses** (`reason=policy_purged`) when the range overlaps a *policy* purge — so a retroactive privacy removal can never be re-cut into a new durable clip (the source chunk mp4 still holds the disabled app's pixels; a policy purge deletes rows, not the mp4). A purge-span read that errors also refuses (fail closed) rather than proceeding. A user (`origin='user'`) delete does not block a cut.

- **Partial-overlap policy purge keeps the clip and RETAINS the overlapping footage — at-rest remanence.** When a retroactive policy purge *partially* overlaps an already-created clip, the propagation **flags but does not re-cut** the clip (full overlap deletes it; user range-deletes never cascade to clips, R11). The clip's mp4 therefore **still contains** the footage the privacy rule removed from the rest of the library, and the clip stays shareable. This is a deliberate keep-the-deliberate-artifact tradeoff, but it is a genuine at-rest residual: the clip's flag copy states the truth ("this clip still contains footage your privacy rules later removed"), so a user is warned before sharing, rather than told the footage was removed when it was not. Re-cutting the purged sub-range out of the clip mp4 is deferred follow-up work.

## Query-parser vocabulary + browser-domain filtering (SCR-179)

The in-app query parser gains a broader, **index-sourced** app/site vocabulary and the ability to filter the timeline by the *site* a browser row visited. Both touch `browser_url`, which is captured pre-scrubber, so the posture is deliberately narrow and adds **no new exposure** beyond what a same-EUID process can already read from the local-only `recording.db`:

- **`/v0/apps.list` returns distinct app names / bundle ids + bare `browser_url` hostnames — never a full URL.** The hostname is extracted (`urlparse(...).hostname`) inside a tight `try/except → None` scope so the secret-bearing path/query (where OAuth codes / session tokens live) never escapes into a frame local that a logged traceback could capture. The returned **hostname list is a same-EUID-only browsing-profile artifact** of the same sensitivity class as `recording.db`: it is derived from local-only data, is **never uploaded / synced / telemetered**, and must never cross the EUID boundary or any export path. Like the other read-only query verbs it is **not audit-logged** and is **excluded from `_idle_shutdown._ACTIVITY_PATHS`**, so vocabulary polling cannot pin an auto-spawned daemon open. A per-kind distinct cap bounds the scan (`truncated` flags a partial result rather than silently capping). v1 returns raw hostnames; stripping private subdomains to eTLD+1 is a deferred further mitigation.

- **`timeline.query` reads `browser_url` only as a filter predicate — it never enters a result row.** When the `app` token might match a site, the handler reads `browser_url` internally, compares the token against the **hostname only** (never the path/query), and keeps or drops the row accordingly. The response row shape is unchanged — exactly `{recording, timestamp_ms, app, title}` — enforced by structural key-set tests. Because nothing token-bearing leaves the daemon, matching adds zero new exposure relative to the existing same-EUID read of `recording.db`. (Note: for a recording that already completed scrubbing, `browser_url` may be the post-scrub value; the filter/vocabulary operate on whatever value is present and do not recover pre-scrub hostnames.)

## Content-index backfill (SCR-178)

The one-shot **backfill** (`screencap backfill`, also driven from the Search consent flow) OCR-indexes a user's *existing* local recordings into the content index so on-screen-text Search covers history recorded before `content_index_enabled` was turned on. It runs as a daemon background job, but its privacy posture is a strict extension of the SCR-118 content-index boundary above — it adds **no new exposure**:

- **Writes only the local `content_index.db` — same sensitivity class as the live OCR index, never uploaded.** The backfill is read-only against recordings (it opens each `recording.db` read-only and never re-scrubs, re-masks, renames, or re-uploads any artifact) and write-only against `content_index.db` plus its own local-only resume ledger (`~/.screencap/backfill_state.db`). Like the live index it holds only **`ALLOW`-classified** on-screen text, is **never part of any uploaded set**, and is **purged on destroy** through the same `delete_recording_interval` path. So the backfilled rows are exactly the same sensitivity class a same-EUID process could already read off disk, and create no new cloud or cross-EUID exposure.

- **The skip set is re-derived over the *intact* local `recording.db` and is fail-closed.** No reusable on-disk block-interval data exists in the correct (`SCRUB_BLOCK_ACTIONS`) form, so the backfill re-runs the canonical classification against each recording's local `recording.db` — which is **not** column-nulled (only the disposable `<name>-scrubbed/` upload copy is nulled; the in-place chunk scrub never nulls the DB; the one mutating path, a retroactive "disable this app," *deletes* whole `window_event`/`action_event` rows and unlinks the matching screenshots). Re-derivation therefore reproduces the canonical block set with no signal loss, and **fails closed** on the two cases where `ALLOW` cannot be positively proven: a screenshot timestamp not covered by any surviving `window_event` (a deleted-row coverage gap — biased outward so an adjacent `ALLOW` window's classification cannot leak across), and a window whose classification genuinely depends on a NULL policy-relevant column (`browser_url`/`title`/`element_state`, detected via raw SQL so the loader's NULL→`''` coercion cannot hide it). The returned skip set is always a **superset** of the live block set, never a subset — a documented **over-skip tradeoff** (a benign frame may go un-indexed) that matches the codebase's fail-closed masking posture: better to miss indexing benign text than to index a masked app's on-screen text. Parity is "identical given identical config": re-derivation reflects the *current* policy, so a policy that tightened since capture can only block *more*.

- **Concurrency converges to "purged," never resurrects.** The backfill OCRs *outside* the shared `content_index_write_lock()`, so a retroactive-disable purge can unlink a now-disabled screenshot while OCR is in flight. Safety rests on the **unlink-before-write barrier**, not the lock alone: the purge (mirroring `scrub_worker`) unlinks screenshots *before* taking the lock, and `index_range` — after acquiring the lock and immediately before `write_chunk` — re-`stat`s each surviving frame's backing screenshot and drops any that were unlinked, so an interleaved purge can never be resurrected in the store (proven by `tests/backfill/test_content_index_contention.py` over both orderings).

- **Progress events are recording-name-free.** The engine and the daemon's `backfill.*` events carry only opaque counters and an ordinal unit index — **never** the recording directory name (which encodes timing/context) — matching the class-name-only/pointer-only bar of the existing query verbs, so a same-EUID EventBus subscriber (including the MCP `/v0/events` subscription) gains no new recording-identifying data flow.

A **deferred stronger mitigation** is tracked as a follow-up: persisting the canonical `SCRUB_BLOCK_ACTIONS` interval set to disk at scrub time so the backfill need not re-derive it. This ships the fail-closed conservative approximation; the residual is the documented over-skip, never an under-block.

## Downloaded local model + bring-your-own endpoint (SCR-239)

Two **opt-in** local segmentation backends run named-task inference on-device. Both inherit the shipped fail-closed privacy strip and per-task consent matrix unchanged; the notes below cover only the new at-rest store and trust boundaries.

- **`~/.screencap/models/` is a new at-rest store — local-only, same-EUID-hardened.** It holds a user-downloaded ~2 GB model, created `0o700` (files `0o600`) with a symlink guard before hashing, matching the `content_index.db` bar. It lives outside `recordings/` and is never uploaded.

- **The download is host+commit+sha256-pinned and installs non-executable formats only.** The model is fetched from a pinned `huggingface.co` at a pinned commit SHA and verified file-by-file against sha256 values recorded at release QA (not live Hub metadata), so a Hub compromise or force-push at that commit cannot install different bytes. Only `safetensors`/`GGUF` are accepted; any `.bin`/`.pt`/`.pickle`/`.ckpt`/`.py` (formats that can execute code on load) is rejected, and the loader runs with `trust_remote_code=False`. A mismatch, disallowed format, interrupted/cancelled download, or insufficient disk aborts symlink-safe and never marks the model installed (fail-closed); the verified staging dir is renamed into place and the `.installed` marker written last, closing the verify→load TOCTOU.

- **Inference runs in a hardened subprocess worker.** The ~2 GB model never stays resident in the all-day daemon (a per-recording subprocess isolates memory + crashes). The worker receives only a privacy-**stripped** activity summary — the provider refuses any summary not marked `stripped=True` *before* spawning (the marker is builder-only-writable; a call-graph guard pins that, and the worker-side check is defense-in-depth, not a trust boundary). The worker launches with a **minimal allowlist env** (no daemon secrets — stronger than the on-device substring denylist) and `HF_HUB_OFFLINE`, so it cannot phone home; its stdin/stdout are size-capped and its stderr is not logged verbatim (it can carry recording-derived text). Model-generated task names are treated as **untrusted output** — sanitized (control-char/markup strip, shape bounds) before persistence, independent of the confidence gate — because they derive from screen content and are surfaced through `/v0/tasks.list` and the MCP surface.

- **The bring-your-own endpoint classifier is the privacy boundary for BYO.** A user-configured local model server is treated as on-device (day-split allowed, nothing leaves) only when its URL is a **loopback literal** (`127.0.0.0/8`, `::1`, `localhost`), canonicalized with `ipaddress`; any other host — including private-LAN IPs, and any DNS name that merely *resolves* to loopback — is REMOTE (a cloud provider: consent-gated, day-split never). Classification is re-enforced at send time: the provider re-classifies the exact endpoint it is about to POST (the value is re-read from config after routing classifies it), pins `localhost` to `127.0.0.1`, and disables redirects — so a config change, a 302, or an off-box resolution fails closed rather than sending a day-split summary. The BYO provider makes daemon-originated outbound requests to a user-supplied URL by design — scoped as same-EUID-accepted; a REMOTE URL could carry credentials in userinfo/query, which are redacted in logs and the settings read-back. The endpoint URL is persisted to `config.toml`, inheriting its existing `0o600` perms.

- **Model-download progress events are recording-name-free.** The daemon's `model.download.*` events carry only bytes/percent + state — no path, no URL, no recording context — matching the `backfill.*` bar.

## Storage-location migration (SCR-228)

The user can relocate the recordings library to another folder **on the same volume** via `/v0/storage.migrate` (an atomic `os.rename`). Three properties define its boundary:

- **`recording.db` stays local-only across the move.** The migration is a pure `os.rename` of the tree — no upload/GCS seam is on the path (a `@pytest.mark.privacy` test asserts the engine imports none), so the R8 local-only guarantee holds unchanged; the DB simply lives at the new local path.

- **The target is rejected if it would exfiltrate the library.** Preflight rejects a **cloud-synced** target — iCloud Drive (`check_icloud_sync`, covering `~/Library/Mobile Documents` + Desktop/Documents sync) and the `~/Library/CloudStorage` File-Provider root plus classic `~/Dropbox`/`~/OneDrive`/`~/Google Drive` — resolving the path with `realpath` first so a symlink into a synced folder is still caught. It also rejects a cross-volume target, a nested target, and a move while `SCREENCAP_RECORDINGS_DIR` pins the location. (Third-party sync tools outside those vendors are a known gap — see the plan's Open Questions.)

- **The new root is hardened, and the move is transactional.** The new recordings root is `chmod`'d `0o700` (the load-bearing cross-user gate — it blocks directory traversal regardless of per-file mode, so a library moved outside `~` to a world-traversable parent is not exposed) and the result is **verified**; a hardening or config-flip failure rolls the `rename` back rather than leaving a half-moved, world-readable, or split-brain state. Same-EUID callers can already move the tree directly, so the verb adds no authz surface beyond the documented boundary.

## Recording toolbar hide controls: global input + capture exclusion

The recording HUD can be dismissed and restored during a recording via a global **⌘⇧H** hotkey and a bottom-edge cursor "peek," alongside the pill's Hide button and the menu-bar item. These touch two surfaces the rest of the app deliberately avoids; both are held to a narrow footprint:

- **Capture exclusion is an invariant, not a styling detail.** Every ScreenCap floating surface shown over recorded content — the HUD pill, the bottom-edge peek bar, and the one-time first-hide hint — is a non-activating `NSPanel` with `sharingType = .none`, so none is ever captured into the user's recording. A ScreenCap surface leaking into a recording is a **blocker**, not a cosmetic bug; the manual-QA capture spot-check (`docs/runbooks/new-ui-manual-qa.md` §4a) guards it, and any new floating surface must carry the same exclusion.

- **The global-input footprint is minimal and recording-scoped.** ⌘⇧H is a single fixed **Carbon `RegisterEventHotKey`** binding — a scoped system hotkey registration, **not** a keystroke-stream tap or event monitor — registered only while a recording is live and unregistered on every teardown (including the imperative abnormal-end path), so ScreenCap observes no input when idle and never reads the user's keystroke stream. The bottom-edge peek reads only the **public `NSEvent.mouseLocation`** on a short recording-scoped poll timer; it is not a mouse-event tap. Consequently the feature needs **no new TCC grant** (neither Accessibility nor Input Monitoring) beyond what recording already requires. This is the deliberate, narrowly-scoped exception to the app's otherwise window-scoped-shortcut posture (the ⌘⇧F "no global tap" decision): ⌘⇧H's purpose is to reach the user while the *recorded* app is focused, which a window-scoped shortcut cannot do.

## Threats in scope

ScreenCap aims to defend against the following:

- **Cross-user access on a shared Mac.** Another macOS user account on the same machine cannot read the socket, read recordings under `~/.screencap/recordings/`, or read the audit log. The `0o700` parent directory and per-user home directory enforce this.
- **Umask drift and accidental permission relaxation.** If `~/.screencap/run/` or `api.sock` is ever chmod-ed outside its expected mode (umask race, manual `chmod`, packaging mistake), the daemon refuses to start rather than serving over a leaky socket.
- **PID-spoofing of advisory provenance.** The provenance classifier knows the peer's PID and argv at probe time are racy (PID reuse, `exec()` between accept and probe). It treats those signals as advisory metadata, never as an auth gate. A caller cannot impersonate the SwiftUI app to bypass authorization, because no authorization decision uses the classification.
- **Caller-supplied metadata tampering.** Clients may send a `started_by` field, but the daemon overrides it with its server-derived classification before persisting. The persisted metadata reflects what the daemon observed, not what the caller claimed.

## Threats out of scope

These threats are *not* defended against by the daemon and require separate mitigations or are explicitly accepted:

- **Malware already running as the same macOS user.** Any process with your effective UID can read `~/.screencap/recordings/`, read the local-only on-screen content index at `~/.screencap/content_index.db` (mode `0600`), connect to the daemon socket, read the audit log, read the short-lived engine ID token from `~/.screencap/run/engine-token-<name>.jwt` (mode `0600`) while a cloud-bound recording is live, read the cloud refresh token from your Keychain (default "Always Allow" ACL), and call any verb — including the read-only content/transcript/timeline query verbs, which expose no more than that process could read from disk directly. Same-user trust is the documented boundary; the daemon is not a sandbox for processes running with your privileges. The macOS TCC subsystem still gates the underlying screen-capture capability — code without Screen Recording permission cannot capture screen content even if it can call `/v0/recording.start` — but the daemon itself does not enforce a per-caller capability check above same-user.
- **Root, administrator, or another user with read access to your home directory.** A process running as root can read anything; a backup tool with full-disk access can copy recordings; another user with sudo can impersonate you.
- **Physical access to an unlocked Mac.** Anyone at the keyboard inherits your session privileges.
- **Compromised dependencies or supply-chain attacks.** Mitigated by Python and Homebrew's own integrity controls, not by the daemon.
- **Side-channel inference from recording metadata.** Filenames, durations, and audit-log peer paths can leak that you recorded *something*, even if the content is encrypted at rest. Treat the audit log and recording directory as the same sensitivity class as the recordings themselves.
- **Cross-account fragmentation in a transient/undeterminable-uid window.** When a cloud recording is pinned to an owner account but the current account cannot be determined at convergence (not signed in, or a transient auth failure), the ownership gate degrades to the normal upload path rather than refusing — the deliberate "never false-refuse over never fragment" tradeoff. Accepted residual; see [Cross-account recording isolation (SCR-116)](#cross-account-recording-isolation-scr-116).

## Alternatives considered

SCR-64 (the ticket that motivated this document) asked whether same-user trust is acceptable for ScreenCap or whether a stronger per-caller authentication mechanism should be added. Two alternatives were considered and rejected.

**Promoting provenance to an enforcement gate.** The daemon already derives a `swiftui` / `cli` / `mcp` / `unknown` classification per peer. One could imagine rejecting `unknown` peers, or only allowing known SwiftUI / CLI binaries. This was rejected because the PID-reuse and time-of-check / time-of-use races on AF_UNIX cannot be closed without code-signing requirement verification (see Scott Knight's [audit tokens writeup](https://knight.sc/reverse%20engineering/2020/03/20/audit-tokens-explained.html) and Quarkslab's [Intego LPE analysis](https://blog.quarkslab.com/intego_lpe_macos_2.html)), and ScreenCap's mixed distribution model (signed `.app` bundle plus unsigned or ad-hoc-signed CLI binaries via Homebrew and source builds) cannot support a stable code-signing requirement string today. The gate would also lock out same-user automation (cron jobs, ad-hoc scripts, future MCP-style tools) without raising the bar against an attacker who can simply invoke the bundled CLI binary directly.

**Bearer token co-installed via SMAppService.** The daemon could generate a random secret on first launch, write it to `~/.screencap/run/api.token` at mode `0o600`, and require clients to send it as an `Authorization: Bearer` header. This was rejected because any process that can connect to the socket can also read the token file (same UID, same directory, same mode), so the token adds no defense against the threat that motivates it. It also introduces worse-than-no-token failure modes: tokens leak into shell history, `ps` output, crash reports, and support bundles, and developers relaxing token-file permissions to debug ("just chmod 644 for a sec") is a documented anti-pattern. This matches Apple's DTS guidance on AF_UNIX IPC and the `ssh-agent` design rationale.

A future option — per-call code-signing verification via `SecCodeCopyGuestWithAttributes` against a Team-ID requirement string — would genuinely raise the bar against a same-user attacker by forcing a Developer ID forgery. It is blocked today by ScreenCap's mixed distribution model and would require its own design pass. The full rationale lives in the [SCR-64 plan](docs/plans/2026-05-25-001-fix-daemon-socket-per-caller-auth-plan.md).

## In-app feedback relay (feat/in-app-feedback-form)

The in-app "Send Feedback" form submits bug reports / feedback / feature requests through a small **unauthenticated** Cloud Function (`submit-feedback`, `scripts/cloud-function/feedback.py`) that files a Linear triage issue. It is the product's **first tokenless endpoint** — every other Cloud Function verifies a Firebase ID token. Anonymous submission is the product requirement (a signed-out user must be able to report a bug), so the boundary is designed around abuse-bounding, not authentication.

- **What a forged request can and cannot do.** With no credential, a request can create **one** Linear triage issue and park **bounded** bytes on Linear's own storage. It can read nothing — there is no data-fetch path, no access to `users/…`, no daemon reach. The blast radius of the endpoint is "spam the maintainer's triage," which the controls below bound.
- **Client-supplied URLs are never trusted.** Attachment bytes never pass through the function: `prepare` mints a Linear `fileUpload` signed URL per file and returns a stateless **HMAC claim** over `{assetUrl, exp}` (signed with `FEEDBACK_HMAC_KEY`, a secret distinct from the Linear key); `submit` embeds an `assetUrl` only if its claim verifies (constant-time), is unexpired, and its host is on the Linear upload-host allowlist. So an anonymous caller cannot render an attacker-chosen URL (phishing link, tracking pixel) in the maintainer's triage. A leaked claim is replayable within its window — an accepted residual, since it only authorizes embedding an asset the claim-holder already minted.
- **Injection-hardened rendering.** The user message renders inside a fenced code block (fence sized past any backtick run); the server-generated metadata block sits below a fixed delimiter; version strings and the optional email are pattern-validated (excluding markdown-breakout characters) and rendered as inline code; client filenames are discarded in favor of server labels. GraphQL calls use static query documents with all user strings confined to `variables`.
- **Browser-CSRF guard.** The function requires `Content-Type: application/json` (forcing a CORS preflight) and emits **no** `Access-Control-Allow-Origin` header, so a malicious web page cannot make visitors' browsers POST forged submissions; the bundled CLI is unaffected.
- **Best-effort rate limiting, honestly scoped.** In-process per-IP request and declared-byte budgets, keyed on the **rightmost** `X-Forwarded-For` entry (Google appends the true peer). Counters live in instance memory, so they are **per-instance-lifetime, not a true hourly quota** — a spam speed-bump paired with `--max-instances=2`, not a hard limit; a durable counter is the deferred upgrade if real abuse appears. Known IP-limit caveats (shared NAT) are accepted at this scale.
- **Least privilege.** The `LINEAR_API_KEY` belongs to a dedicated Linear account whose access is restricted to the Screencap team, held in Secret Manager, never returned to the client or logged (upstream Linear error text is never forwarded; the client-facing `server` error is opaque). The function runs as a dedicated service account holding only Secret Manager accessor on its two secrets — the broad default compute account never sits behind this endpoint.
- **Outbound PII posture.** The message, the optional (user-clearable) email, attachments, and app/daemon/macOS version metadata terminate at Linear under Linear's retention policy. Anonymous reporters have no deletion path for that content — an accepted v1 residual, stated rather than implied. The feedback path reads **nothing** from the recording data plane: no `recording.db`, no library screenshots, no window titles, no logs — only the exact files the user attached (a CI privacy-lane test pins this).
- **Accepted residuals.** Content-type is validated as declared (not by inspecting bytes; Linear's signed PUT header-binds the stored type); the Linear upload-host allowlist is pending confirmation by the U0 pre-flight spike against the real workspace.

## Reporting a vulnerability

Please report security vulnerabilities **privately** via GitHub's "Report a vulnerability" form on the [Security Advisories page](https://github.com/proteus-computer-use/screencap/security/advisories/new). This opens a private channel with the maintainers and avoids public disclosure before a fix is available.

If you cannot use GitHub for any reason, you may instead open a regular issue marked `[SECURITY]` requesting a private contact channel — but please do **not** include vulnerability details in the public issue.

We aim to acknowledge reports within three business days and to publish a coordinated advisory once a fix is shipped.
